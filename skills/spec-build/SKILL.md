# spec-build — 구현계획 PR 하나 구현

입력은 `spec-write` 가 확정한 명세와 구현계획이다. 이 매뉴얼은 **무엇을**이 아니라 **어떻게** 일하나를 정한다.
세션 하나 = 구현계획의 PR 하나. 다음 PR 은 새 세션에서 한다 (컨텍스트를 새로 시작하는 효과).

## 입력과 위치

- 주제 폴더: **메인 체크아웃**의 `.requirements/<주제>/` — `구현계획.md`, 명세 md, `진행.md`.
  워크트리 안에 있어도 메인 경로에 쓴다: `dirname "$(git rev-parse --path-format=absolute --git-common-dir)"`.
- 주제·번호는 말에서 찾는다. 단위 이름("로그인")이면 구현계획 순서표에서 번호를 찾는다.
  주제가 모호하면 `.requirements/*/구현계획.md` 목록에서 고르게 한다.
- PR 번호(구현계획의 순서 번호)가 없으면 `진행.md` 에서 머지 안 된 첫 번호를 제안하고 확인받는다.
- 장부: `진행.md` (`files/진행-템플릿.md`). 없으면 만든다. 워크트리 격리 세션은 메인 경로에 쓰지 못한다 —
  그때는 세션 scratchpad 에 쓰고 `check_progress.py` 도 그 파일로 돌린 뒤, `/cleanup` 으로 워크트리를 나와 메인 경로로 복사한다.
  대화가 압축되면 기억보다 **`진행.md` 와 `git log`** 를 믿는다.

## 순서

1. **읽기.** 구현계획의 N번 절, 그 명세 md, `진행.md` 를 읽는다. N번이 이미 진행 중이면(상태가 `시작`·`로컬 테스트 대기`·`PR 올림`)
   이어서 한다 — 끝난 커밋을 다시 만들지 않는다.
   N번이 맡은 명세 `테스트 목록` 줄을 `진행.md` 테스트 표에 옮긴다. 명세에 테스트 목록이 없으면(테스트 목록 도입 전 명세)
   바뀐 흐름(신규형은 만들 것)과 구현계획 `테스트:` 칸에서 `조건 → 기대 결과` 로 뽑아 옮기고, 판정 줄로 남긴다.
2. **선행 확인.** N번의 "먼저 끝나야 하는 것" 에 적힌 PR 이 `gh pr view <번호> --json state` 로 `MERGED` 가 아니면
   **멈추고 보고**한다. "없음" 이면 진행.
3. **`/brief`** 로 그 영역의 최근 PR 결정 기록·열린 PR·규칙을 불러온다.
4. **`/ax-ws-create`** 로 `origin/develop` 에서 워크트리를 만든다. `진행.md` 에 N번 절을 만들고 상태 `시작`, 브랜치를 적는다.
5. **명세와 지금 코드 대조.** 명세는 과거 시점이다. `graphify affected "<바꿀 대상>"`·`graphify query` 로 영향 범위와
   기존 헬퍼·패턴을 찾고 실제 파일로 확인한다. 명세의 "현재 흐름"(신규형은 "기존과 붙는 곳") 과 코드가 다르면 아래 결정 규칙으로 처리하고 보고한다.
6. **구현 (TDD).** 커밋 마일스톤 순서대로, 그 안에서 테스트 표의 **줄 하나씩** 이 순환을 돈다.
   실행·판정·커밋·기록은 `files/tdd.py` 한 번의 호출로 한다(손으로 커밋·기록하지 않는다 — 호출 수가 토큰이다).
   1. **실패** — 그 줄의 테스트 하나를 쓴다. 아직 없는 이름이면 **빈 껍데기**(이름만, 빈 결과)를 먼저 만들어
      단언에서 실패하게 한다. 그리고
      `python3 ~/.claude/skills/spec-build/files/tdd.py red <진행.md> <N> "<줄>" --files <테스트·껍데기> -- "<명령>"`.
      기대한 이유로 실패해야 커밋된다(import·이름 없음·문법 오류·테스트 0개·통과는 거부). 실패 칸에 이유와 커밋이 적힌다.
   2. **통과** — 그 테스트를 통과시키는 **가장 작은** 코드만 쓴다. 다음 줄의 일을 미리 하지 않는다.
      `tdd.py green <진행.md> <N> "<줄>" --files <구현> -m "<type>: <제목>" -- "<명령>"`.
      명령은 그 테스트와 그 영역 기존 테스트를 함께 돌리는 것으로.
   3. **정리** — 테스트가 초록인 채로 중복·이름을 정리하고, 다시 돌려 초록이면 `refactor:` 로 커밋한다(필요할 때만).
   - 종류가 화면이면 `/dev` 로 띄워 스크린샷, 설정이면 그 파일을 읽는 명령을 실행해 `통과` 칸에 남긴다(`실패` 칸은 `-`).
   - 테스트 표에 없는 동작이 필요해지면 → 결정 규칙(명세가 말하지 않는 내부 구현인지, 동작이 바뀌는지).
   - 코드는 ponytail(full) 기준: 기존 헬퍼·패턴 재사용, 요청 없는 옵션·추상화 금지, 근본 원인을 공유 코드에서 한 번,
     주변 코드와 같은 이름·구조·주석 밀도. 입력 검증·데이터 손실 방지·보안은 줄이지 않는다.
   - 커밋은 `git-commit` 규칙. 명세 밖 결정을 했으면 **같은 시점에** `진행.md` 판정 줄을 쓴다.
7. **PR 전 점검.** `/dev` 가 떠 있으면 먼저 멈춘다(검증이 커밋을 옮겨 다닌다).
   0. `tdd.py verify <진행.md> <N>` — 로직 줄마다 실패 커밋에서 다시 실패, HEAD 에서 통과를 확인하고 완료 증거 한 줄을 쓴다.
      이후 커밋이 더 생기면 다시 돌린다.
   1. `/ponytail-review` 를 돌려 지적을 고치거나, 고치지 않으면 판정으로 남긴다.
   2. `/ponytail-debt` 의 `shortcut:` 목록을 `진행.md` 에 옮긴다.
   3. `진행.md` 명세 대조표를 채운다 — 명세 "바뀐 흐름"(신규형은 "만들 것") 항목마다 코드 위치와 증거.
   4. `python3 ~/.claude/skills/spec-build/files/check_progress.py <진행.md> <N>` 이 통과해야 다음으로 간다
      (로직 줄마다 실패 커밋·통과 기록, 지금 HEAD 로 verify 통과, 명세 대조표 빈칸 0, 완료 증거).
8. **로컬 테스트 넘기기.** 사용자가 직접 돌려 보기 전에는 `/pr` 하지 않는다.
   1. 화면·API 가 걸리면 `/dev` 로 지금 워크트리 서버를 띄운다.
   2. `진행.md` `로컬 테스트` 표에 항목마다 **어디서**(URL·명령) · **무엇을**(누를 것·입력값) · **기대 결과** 를 적는다.
      재료는 명세 "바뀐 흐름"(신규형은 "만들 것")과 테스트 표. 자동 테스트로 증명된 내부 로직은 빼고, 사람이 봐야 하는
      화면·흐름·실제 데이터·설정 반영을 넣는다. 멈춤 규칙이 걸리는 항목은 조건을 적는다(예: 문자는 본인 번호로만).
   3. 같은 표를 채팅으로 주고 **멈춘다**. 상태 `로컬 테스트 대기`.
   4. 답에 따라 — "통과"·"올려" → 결과 열을 채우고 9로. 문제 보고 → 로직이면 테스트 표에 줄을 더해 6의 순환으로 고치고
      (명세와 다르게 가야 하면 결정 규칙대로 멈춤), 7을 다시 돌린 뒤 바뀐 항목만 다시 준다.
      "테스트 없이 올려" → 표 아래에 `로컬 테스트 생략 — 사용자 지시` 를 적고 9로.
9. **`/pr`.** PR 본문 `### 배경` 에 명세 대조표를 줄여 넣는다 — 목록(`-`) 말고 **표나 문장**으로, 1,500자 이하
   (Rumi 는 `배경`·`요약` 절의 목록 아닌 줄만 2,000자까지 읽는다). 판정 줄은 결정 기록의 재료다.
   상태 `PR 올림 #<번호>`. 이후는 `/pr-review-loop` 가 이어서 한다: Rumi 차단 지적 수정 → APPROVE → 결정 기록 →
   **"PR #N 머지할까요?" 사람 승인** → `/pr-merge` → `/cleanup`.
10. **머지 뒤.** 메인 체크아웃에서 `graphify update .`, `진행.md` 상태 `머지 <sha>`. 사용자가 `나중에` 를 고르면 상태 `리뷰 통과` 로 두고 끝낸다.
11. **보고.** 판정 목록(전부, 순서대로, 틀렸을 때 비용 포함) · Rumi low 참고 · shortcut 목록 · 다음 PR 번호.

## 결정 규칙

- 명세와 다르게 가야 하는데 **사용자에게 보이는 동작·데이터(테이블·저장 값)·API 모양·범위(다른 앱·파일)·S-0 배포 설정**이
  바뀐다 → 멈춘다. `spec-write` 으로 명세를 고치고 사용자 확인 뒤 구현.
- 명세가 말하지 않는 내부 구현(이름·파일 나누기·헬퍼 선택) → 직접 정하고 판정 줄 `무엇을 — 왜 — 틀렸을 때 비용` 을 남기고 계속.
- 명세의 "현재 흐름"·"기존과 붙는 곳" 이 지금 코드와 다르다 → 위 두 규칙 중 해당하는 쪽.
- 테스트가 처음부터 통과한다 → 테스트가 틀렸다. 실패하도록 고친다.
- 실패 이유가 기대 결과가 아니다(import 오류·오타·환경) → 실패로 치지 않는다. 원인을 고치고 다시 본다.
- 아직 없는 함수·화면이라 "이름 없음" 으로만 실패한다 → 빈 껍데기를 만들고 단언에서 실패하는 것을 본다.
- `tdd.py` 가 거부했다 → 그 판정을 따른다. 손으로 커밋·기록해 우회하지 않는다.
- 테스트 여러 개를 한꺼번에 쓰고 싶다 → 쓰지 않는다. 줄 하나씩 실패 → 통과 → 정리.
- 테스트 결과가 계획과 다르다 → 코드가 틀렸으면 전역 §7(재현→가설→근본 원인), 계획이 틀렸으면 첫 두 규칙.
- 그 주제에 `구현계획.md` 가 없다(명세 미확정) → 구현하지 않는다. `spec-write` 으로 넘어간다.
- 선행 PR 이 머지 전이다 → 멈춘다. 앞 PR 브랜치 위에 쌓지 않는다.
- graphify 그래프가 없다 → grep 으로 대신한다. 그래프를 자동 생성하지 않는다(전역 §8).
- 레포의 멈춤 규칙(원격 DB 쓰기, S-0, 문자 실발송 등)은 이 매뉴얼보다 우선한다.

## 완료 기준

1. `check_progress.py` 통과 — 로직 줄마다 실패 커밋·통과 기록, 지금 HEAD 로 `tdd.py verify` 통과, 명세 대조표 빈칸 0 (자동 검사)
2. 증거는 **이번 세션에서 실행한** 명령과 결과다. "통과할 것이다" 는 증거가 아니다
3. `/ponytail-review` 지적이 전부 고쳐졌거나 판정으로 남았다
4. `진행.md` `로컬 테스트` 표의 결과 열이 사용자 답으로 채워졌거나 `로컬 테스트 생략 — 사용자 지시` 가 있다 (PR 전)
5. Rumi APPROVE → 사람 머지 승인 → `/pr-merge` 결과 `merged` → `/cleanup`
6. `graphify update .` 실행, `진행.md` 상태 `머지 <sha>`

## 하지 않는 것

- 하위 에이전트 호출 (레포 절차가 정한 `/pr-merge` 별도 컨텍스트는 예외)
- 판정 줄 없이 구현계획에서 벗어나기
- 사람 승인 없이 머지 (자동 머지로 바꿀 때는 이 매뉴얼이 아니라 `/pr-review-loop` 의 머지 확인을 바꾼다)
- 한 세션에서 PR 여러 개
- 워크트리 안 `.requirements/` 에 쓰기

## 파일

- `files/INDEX.md` — 파일 목록
- 고친 기록은 `notes.md`
