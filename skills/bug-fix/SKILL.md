# bug-fix — 버그 하나 고치기

조건: **이미 있는 동작이 의도와 다르다.** PR 제목 type(`fix:`)이 아니라 이 조건으로 쓴다.
세션 하나 = 버그 하나 = PR 하나. 하위 에이전트 없이 메인 세션이 직접 한다.

| 상황 | 매뉴얼 |
|---|---|
| 원하는 동작을 새로 만들거나 바꿈 | `spec-write` → `spec-build` |
| 열린 PR 안의 Rumi 지적 (범위 안) | `/pr-review-loop` |
| 이미 있는 동작이 의도와 다름 (Rumi 범위 밖 지적 포함) | **bug-fix** |

## 순서

1. **증상 정리.** 무엇이 · 언제 · 어디서(앱·화면·명령) · 기대한 것과 실제 결과. 오류 문장과 스택은 끝까지 읽는다.
2. **버그인지 판정.** 의도가 기록된 곳과 대조한다 — 명세(`.requirements/`), 그 코드를 만든 PR 의 `## 결정 기록`, 문서, 기존 테스트.
   - 기록과 코드가 다르다 → 버그. 진행.
   - 기록이 없거나, 고치면 기록에 없는 동작이 새로 생긴다 → 한 줄로 묻는다: "버그로 고칠까요, 명세부터 쓸까요?"
3. **급한가.** 운영 사용자에게 영향이 있고 다음 배포를 기다릴 수 없어 보이면 "hotfix 로 갈까요?" 를 한 줄로 묻는다.
   hotfix 면 `docs/agents/git-flow-detail.md` 를 읽고 그 절차를 따른다(main 분기 → main squash → `sync/*` 로 develop 동기화까지).
4. **`/brief`** — 그 코드를 최근에 바꾼 PR·결정 기록. 버그는 최근 변경에서 온 경우가 많다: `git log -S <기호>`.
5. **`/ax-ws-create`** (hotfix 가 아니면 `origin/develop` 에서).
6. **운영 증거 수집 (읽기만).** 로그, Slack 알림, Rumi 장부, 원격 mvpdb **SELECT**. 여러 부품이 걸리면(워크플로 → 스크립트 → 앱)
   경계마다 들어가고 나오는 값을 한 번에 모아 **어디서 깨지는지**부터 좁힌다.
7. **재현.**
   - 로직 → **실패하는 자동 테스트**. 운영 조건(재시작·한도 초과·다른 DB)은 테스트 안에서 흉내 내도 된다.
   - 화면 → `/dev` 로 띄워 **고치기 전** 스크린샷.
   - 실패 테스트는 수정과 **따로 먼저 커밋**하고, 실패 출력을 기록해 둔다(이후 증거).
   - 흉내 내기도 안 되면 고치지 않는다 → 모은 증거와 남은 가설을 보고하고 멈춘다.
8. **근본 원인.** 가설 하나를 문장으로("X 가 원인, 왜냐하면 Y") 세우고 가장 작은 확인으로 반증한다. 틀리면 새 가설 — 위에 덧대지 않는다.
   잘 되는 비슷한 코드와 비교해 차이를 전부 적는다. 틀린 가설은 작업 기록 재료로 남긴다.
9. **수정.** 근본 원인 자리에서 한 번. ponytail(full) 기준 — "고치는 김에" 정리·리팩터링 금지.
   - 원인이 같고 **같은 앱 안**인 다른 곳 → 함께 고치고 각각 테스트.
   - **다른 앱·동료 소유 영역** → 고치지 않고 위치만 찾는다(PR 본문 `### 배경` 에 문장으로, 보고에도).
   - 공유 코드가 원인 → 그 한 곳만 고치고 `graphify affected "<기호>"` 로 쓰는 앱을 확인해 보고.
10. **확인.** 재현 테스트가 통과, 그 영역의 기존 테스트도 통과. 화면은 **고친 뒤** 스크린샷. `/ponytail-review`.
11. **`/new-pr`.** PR 본문 `### 배경` 에 **문장으로**(목록 말고 — Rumi 는 `배경` 의 목록 아닌 줄만 읽는다):
    증상 · 근본 원인 · 왜 그 자리에서 고치나 · 재현 테스트 이름 · 범위 밖에 남은 같은 패턴. 틀린 가설·시도는 `.done/` 작업 기록에.
    이후 `/pr-review-loop` → Rumi 지적 수정 → APPROVE → **사람 머지 승인** → `/pr-merge` → `/cleanup`.
12. **머지 뒤.** 메인 체크아웃에서 `graphify update .`. 보고: 근본 원인 한 줄 · 재현 테스트 · 범위 밖 같은 패턴 위치.

## 결정 규칙

- 의도 기록과 다르다 → 버그. 기록이 없거나 새 동작이 생긴다 → 묻는다.
- 재현 못 함(흉내도 불가) → 고치지 않고 보고.
- 테스트가 수정 전에도 통과한다 → 재현이 아니다. 테스트를 고친다.
- 수정을 3번 해도 안 된다 / 고칠 때마다 다른 곳에서 문제가 나온다 → 멈춘다. 구조 문제로 보고 상의.
- 고치다 보니 원하는 동작을 바꿔야 한다 → 멈추고 `spec-write`.
- 운영 장애로 보인다 → hotfix 여부를 묻는다. 직접 정하지 않는다.
- 원격 DB 쓰기·S-0 배포 설정·문자 실발송 등 레포 멈춤 규칙은 이 매뉴얼보다 우선한다.

## 완료 기준

1. 재현 테스트가 **수정 전 커밋에서 실패**하고 **수정 후 통과**한 출력이 이번 세션에 있다 (화면은 전·후 스크린샷)
2. 그 영역 기존 테스트 통과, `/ponytail-review` 지적 처리
3. PR 본문 `### 배경` 에 근본 원인이 문장으로 있다
4. Rumi APPROVE → 사람 머지 승인 → `/pr-merge` `merged` → `/cleanup` → `graphify update .`

## 하지 않는 것

- 재현 없이 추측으로 고치기, 증상만 막기(예외 삼키기·조건 하나 더 걸기)
- 다른 앱·동료 소유 코드 수정
- 하위 에이전트 호출 (레포 절차의 `/pr-merge` 별도 컨텍스트는 예외)
- 열린 PR 안의 범위 안 Rumi 지적을 이 매뉴얼로 처리
- 사람 승인 없이 머지, hotfix 여부 직접 결정

## 파일

- 고친 기록은 `notes.md`
