# spec-write — 명세서 작성·확정

방법론은 **SDD(명세 먼저 개발)** 다. 명세서가 읽히지 않으면 사람은 읽기를 건너뛰고 구현부터
하게 되고, 그러면 SDD 가 무너진다. 그래서 **최우선 기준은 읽기 쉬움**이다 — 한 파일을 5분 안에
읽고 무엇이 바뀌는지 한눈에 알아야 한다.

## 언제 쓰나

- docs 가 아닌 변경은 **크기와 상관없이 전부** 명세서가 먼저다. 한 줄 수정도 마찬가지.
- `.claude/`(commands·skills·rules·agents), `AGENTS.md`, `CLAUDE.md` 는 동작을 바꾸므로 docs 가 아니다 → 명세서 필요.
- **예외: 리뷰 지적(Rumi 등) 수정.** 이미 명세서가 있는 PR 범위 안에서 지적을 고치는 일은 새 명세서가 필요 없다.
  단 고치다가 명세와 다르게 가야 하면 명세서부터 고친다.
- **예외: 버그 수정.** 이미 있는 동작이 기록된 의도(명세·결정 기록·문서·테스트)와 다르면 `bug-fix` 로 고친다.
  고치면 기록에 없는 동작이 새로 생기거나 기록이 없으면 사용자에게 묻는다.
- 조사 요청("찾아 줘")으로 시작했어도, 고칠 곳이 나오면 **구현하지 말고** 이 매뉴얼로 넘어온다.
  사용자가 "설계서 먼저"라고 지적한 적이 있는 실수다.

## 입력과 위치

- 세션: **메인 체크아웃 세션**에서 한다. 워크트리 세션은 메인 경로에 쓰지 못해 사용자에게 `cp` 를 넘기게 되고,
  워크트리 사본은 정리할 때 조용히 사라진다. 시작할 때 `git rev-parse --path-format=absolute --git-dir` 와
  `--git-common-dir` 가 다르면 워크트리다 → 아무것도 쓰지 말고 멈춰 "메인 체크아웃(`<메인 경로>`) 세션에서 다시 요청" 을 안내한다.
- 저장 위치: 메인 체크아웃의 `.requirements/<주제>/` (git 제외 폴더).
  메인 경로: `dirname "$(git rev-parse --path-format=absolute --git-common-dir)"`.
  메인 체크아웃에서 쓰는 것은 이 폴더뿐이다 — 코드·설정은 고치지 않는다 (구현은 `spec-build` 가 워크트리에서).
- `<주제>` 와 파일 이름은 Claude 가 정한다. 짧은 한국어 명사구(예: `pr-merge-토큰효율`).
- 작은 수정도 **항상 폴더**를 만든다.

```
.requirements/<주제>/
├── 00-개요.md        큰 그림 (작은 수정이면 이 파일 하나로 끝)
├── 01-<단위>.md      쪼갠 명세 (00 이 5분을 넘을 때만)
└── 구현계획.md        확정 뒤에만 만든다
```

## 순서

1. **조사.** 현재 흐름(신규형은 붙을 기존 부분)을 실제 코드·로그·실측으로 확인한다. 사실마다 근거(파일:줄, 실행한 명령과 결과)를 남긴다.
   추측으로 현재 흐름을 쓰지 않는다.
2. **핵심 흐름 대화.** 파일을 쓰기 전에, 앱이 하는 일의 큰 줄기를 사용자와 **대화로 한 단계씩** 정한다.
   사용자가 LLM 이 어디서 쓰이는지도 모른 채 구현한 적이 있다(Janus) — 세부 파일이 많아도 큰 줄기가 안 보이면 생기는 일이다.
   - Claude 가 조사 결과로 **대표 상황 하나**(누가 무엇을 하려고)를 골라, 처음부터 끝까지 7단계 이내 흐름 초안을 채팅에 보여 준다.
     변경형은 고친 뒤의 대표 상황이다.
   - 단계마다 아래를 **한 번에 질문 하나씩** 묻고 정한다. Claude 가 근거(코드·실측·참고 사례)가 있으면 추천안과 이유를 함께 낸다.
     - 누가 하나 — 사람·화면·서버·LLM·외부 시스템 중 무엇
     - 무엇이 들어가고 무엇이 나오나 — 예시 값으로 (예: "내일 일정 알려 줘" → 일정 3건 목록)
     - 누가 판단하나 — 정해진 규칙(코드)·그때그때 판단(LLM)·사람·외부 시스템. LLM 이면 무엇을 보고 무엇을 고르는지, 질문 하나에 몇 번 불리는지
     - 실패하거나 틀리면 어떻게 되나 — 멈춤·재시도·사람에게 알림
   - 사용자가 이미 정해 말한 것은 다시 묻지 않고 "이렇게 이해했다" 로 확인만 한다. 사용자 답이 다른 단계를 바꾸면 그 단계로 돌아간다.
   - 단계를 다 정하면 흐름 전체를 표로 한 번 더 보여 주고 확인받는다. **확인 전에는 세부 명세를 쓰지 않는다.**
3. **틀 고르기.** 파일마다 틀 하나를 고른다 (아래 결정 규칙 "틀").
   - **변경형** `files/명세-템플릿-변경.md` — 이미 있는 동작을 고친다. 뼈대 **현재 흐름 → 고칠 곳 → 바뀐 흐름**.
   - **신규형** `files/명세-템플릿-신규.md` — 고칠 현재가 없다. 뼈대 **목적과 쓰는 사람 → 만들 것 → 기존과 붙는 곳**.
4. **크기 판단.** 다 쓰면 4,000자(5분)를 넘을 것 같으면 `00-개요` 에는 큰 그림만 두고 단위별로 `01-`, `02-` 로 쪼갠다.
   각 파일이 각각 5분 안에 읽혀야 한다.
5. **작성.** 고른 틀의 템플릿을 따른다.
   - 맨 앞에 **용어표**, 그다음 **핵심 흐름** 표 — 2단계에서 확인받은 흐름 그대로. 쪼갠 경우 `00-개요` 에만 두고,
     세부 파일은 `한눈에 보기` 에 핵심 흐름의 몇 번 단계를 다루는지 적는다. 본문에 나오는 약어·영문 용어·앱 이름 중 사용자가 모를 수 있는 것은 전부 여기서 한 줄로 푼다.
   - 내부 코드명(P1, D4, Q3, AC-10 같은 것)을 만들지 않는다. **우리말 이름**으로 부른다
     (`D4` → "결정 기록 먼저 쓰기").
   - 실측표·대안 비교 같은 상세는 핵심 결론 한 줄만 본문에 두고, 꼭 필요하면 쪼갠 명세로 보낸다.
   - **테스트 목록**: 바뀐 흐름(신규형은 만들 것) 항목마다 `조건 → 기대 결과` 한 줄 이상(종류: 로직·화면·설정). 명세를 확정할 때
     무엇을 증명할지도 함께 확정된다. 쪼갠 경우 `00-개요` 에는 단위를 잇는 확인을 둔다.
6. **검사.** `python3 ~/.claude/skills/spec-write/files/check.py <폴더>` 를 돌려 전부 통과할 때까지 고친다 (아래 "완료 기준").
7. **보고.** md 경로를 알려 준다. 정할 것이 남았으면 명세서에 질문 목록으로 쌓지 말고,
   **대화로 하나씩 차례대로** 설명하고 묻는다. 정해지면 본문을 그 결론으로 고친다.
8. **개정.** 사용자가 이해 안 되는 곳을 짚으면 그 곳은 명세서의 결함이다 — 설명을 채팅으로 끝내지 말고 본문을 고친다.
   개정 이력("N차 반영", 변경 내역)은 남기지 않는다. **최종본만** 둔다. 폐기한 안은 본문에서 지운다.
9. **이해 확인.** 사용자가 더 보완할 것이 없다고 하면, 확정 전에 핵심 흐름에 대한 질문 2~3개를 **하나씩** 묻고 사용자가 자기 말로 답한다.
   질문은 흐름의 뼈대에서 고른다: "LLM 은 어느 단계에서 몇 번 불리나", "누구 권한으로 조회하나", "어느 단계가 실패하면 사용자는 무엇을 보나".
   답이 막히거나 명세와 다르면 그 단계는 명세서의 결함이다 → 2단계처럼 그 단계를 다시 대화로 정하고 본문을 고친 뒤 다시 묻는다.
   사용자가 건너뛰자고 명시하면 건너뛰고 보고에 "이해 확인 건너뜀" 을 적는다.
10. **확정.** 이해 확인을 마치면 확정이다. 그러면 `files/구현계획-템플릿.md` 로 `구현계획.md` 를 만든다:
   구현 단위(PR) 목록, PR 마다 맡을 테스트 목록 줄과 커밋 마일스톤. 테스트 목록의 모든 줄이 어느 PR 엔가 들어간다.
   장부 `진행.md` 도 `~/.claude/skills/spec-build/files/진행-템플릿.md` 로 함께 만든다 (워크트리의 `spec-build` 가 새로 만들지 않게).
11. **멈춘다.** 구현은 사용자가 지시할 때 `spec-build` 매뉴얼로 PR 하나씩 시작한다.

## 결정 규칙

- docs 만 바꾸나? → 이 매뉴얼 불필요. `.claude/`·`AGENTS.md`·`CLAUDE.md` 가 걸리면 docs 아님.
- 리뷰 지적 수정이고 그 PR 에 명세서가 있나? → 불필요. 명세 범위를 벗어나면 필요.
- 이미 있는 동작이 기록된 의도와 다른 버그인가? → 불필요, `bug-fix`. 새 동작이 생기면 필요.
- 4,000자 넘나? → 쪼갠다. 줄이기 어렵다고 5분 기준을 늘리지 않는다.
- 용어를 풀어 쓰기 어렵다? → 그 용어를 쓰지 않는 문장으로 바꾼다.
- 틀: 사용자가 지금 보는 동작이나 지금 저장되는 데이터가 바뀌나? → 변경형. 기존은 그대로 두고 새것만 더하나? → 신규형.
- 틀이 섞인다(예: 기존 앱에 새 화면 추가)? → 새 화면 자체는 신규형, 기존 메뉴·권한·테이블에 붙이는 연결은 `기존과 붙는 곳` 에 근거와 함께.
  붙이려고 기존 동작을 바꿔야 하고 그 변경이 한 줄 설명을 넘으면 그 부분만 변경형 파일로 쪼갠다. 한 파일에 두 틀의 절을 섞지 않는다.
- 쪼갠 폴더 안 파일마다 틀이 달라도 된다. `00-개요` 는 폴더 전체의 중심이 고치기면 변경형, 만들기면 신규형.
- 쓰는 사람마다 흐름이 달라 대표 상황을 하나로 못 고르겠다? → 가장 자주 쓰는 사람의 흐름 하나만 핵심 흐름에 두고,
  나머지는 세부 파일에 "핵심 흐름 N단계와 다른 점" 으로 쓴다.
- 핵심 흐름이 7단계를 넘는다? → 묶는다. 묶인 단계의 세부는 쪼갠 파일로.
- 사용자가 "알아서 정해" 라고 한다? → 추천안으로 정하되, 판단(LLM·코드) 칸과 실패 칸은 표로 보여 주고 확인받는다.
- 현재 흐름·기존과 붙는 곳을 확인 못 했다? → 확인 못 했다고 명세서에 적고 사용자에게 묻는다. 추측으로 채우지 않는다.
- 구현 중 명세와 다르게 가야 한다? → 명세서를 먼저 고치고 사용자 확인 뒤 구현한다.
- 비용을 줄이려고 품질(검토 횟수·범위·모델)을 깎는 안인가? → 추천하기 전에 품질 영향을 실측한다
  (빠지는 결과가 실제로 쓸모 있었는지, 대안이 정말 싼지). 실측 없이 "절감"만으로 추천하지 않는다.

## 완료 기준 (check.py 가 1~8 을 검사)

1. 폴더 안 모든 md 가 본문 4,000자 이하 (코드 블록 제외)
2. 모든 md 에 `용어` 절이 첫 절로 있다
3. 모든 명세 md 가 두 틀 중 하나의 절을 다 갖는다 (`구현계획.md` 제외) — 변경형 `현재 흐름`·`고칠 곳`·`바뀐 흐름`,
   신규형 `목적`·`만들 것`·`기존과 붙는 곳`. 두 틀의 절을 섞으면 실패
4. 내부 코드명 패턴(`P1`, `D4`, `Q3`, `AC-10` 등) 0건
5. 개정 이력·미결 표시(`N차`, `반영 이력`, `TBD`, `미정`) 0건
6. 모든 명세 md 에 `테스트 목록` 표가 있고 줄마다 `조건 → 기대 결과` 다 (빈칸·자리표시 없음)
7. (확정 뒤) `구현계획.md` 의 PR 마다 `테스트:` 줄이 1개 이상 있다
8. 첫 명세 md(`00-개요`, 파일 하나면 그 파일)에 `핵심 흐름` 표가 있고, 1~7단계, 칸이 다 채워졌고, `판단` 칸이 사람·코드·LLM·외부 중 하나로 시작한다
9. (사람이 확인) 현재 흐름·기존과 붙는 곳의 사실마다 근거가 있다, 테스트 목록의 모든 줄이 어느 PR 엔가 들어갔다,
   핵심 흐름을 대화로 확인받았다, 이해 확인을 했다(또는 사용자가 건너뛰었다고 보고했다)

## 하지 않는 것

- 명세서 없이 구현 시작, "간단하니까" 예외 두기
- 핵심 흐름을 대화로 확인받기 전에 세부 명세 쓰기, 흐름 초안을 질문 여러 개와 함께 한꺼번에 던지기
- 워크트리 세션에서 명세 쓰기 (워크트리 사본·scratchpad 에 쓰고 사용자에게 복사 맡기기 포함)
- 질문 목록을 명세서에 쌓아 두고 사용자가 읽게 하기
- 기존 `.requirements/` 설계서 소급 정리 (새 설계부터 적용)
