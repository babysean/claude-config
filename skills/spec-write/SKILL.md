# spec-write — 명세서 작성·확정

방법론은 **SDD(명세 먼저 개발)** 다. 명세서가 읽히지 않으면 사람은 읽기를 건너뛰고 구현부터
하게 되고, 그러면 SDD 가 무너진다. 그래서 **최우선 기준은 읽기 쉬움**이다 — 한 파일을 5분 안에
읽고 무엇이 바뀌는지 한눈에 알아야 한다.

## 언제 쓰나

- docs 가 아닌 변경은 **크기와 상관없이 전부** 명세서가 먼저다. 한 줄 수정도 마찬가지.
- `.claude/`(commands·skills·rules·agents), `AGENTS.md`, `CLAUDE.md` 는 동작을 바꾸므로 docs 가 아니다 → 명세서 필요.
- **예외: 리뷰 지적(Rumi 등) 수정.** 이미 명세서가 있는 PR 범위 안에서 지적을 고치는 일은 새 명세서가 필요 없다.
  단 고치다가 명세와 다르게 가야 하면 명세서부터 고친다.
- **예외: 버그 수정.** 이미 있는 동작이 기록된 의도(명세·결정 기록·문서·테스트)와 다르면 `bug-fix` 로 고친다.
  고치면 기록에 없는 동작이 새로 생기거나 기록이 없으면 사용자에게 묻는다.
- 조사 요청("찾아 줘")으로 시작했어도, 고칠 곳이 나오면 **구현하지 말고** 이 매뉴얼로 넘어온다.
  사용자가 "설계서 먼저"라고 지적한 적이 있는 실수다.

## 입력과 위치

- 저장 위치: **메인 체크아웃**의 `.requirements/<주제>/` (git 제외 폴더). 워크트리 안에서 일하고 있어도
  메인 체크아웃 경로에 쓴다 — 워크트리 사본은 정리할 때 조용히 사라진다.
  메인 경로: `dirname "$(git rev-parse --path-format=absolute --git-common-dir)"`.
- `<주제>` 와 파일 이름은 Claude 가 정한다. 짧은 한국어 명사구(예: `pr-merge-토큰효율`).
- 작은 수정도 **항상 폴더**를 만든다.

```
.requirements/<주제>/
├── 00-개요.md        + 00-개요.html       큰 그림 (작은 수정이면 이 파일 하나로 끝)
├── 01-<단위>.md      + 01-<단위>.html     쪼갠 명세 (00 이 5분을 넘을 때만)
└── 구현계획.md        + 구현계획.html        확정 뒤에만 만든다
```

## 순서

1. **조사.** 현재 흐름(신규형은 붙을 기존 부분)을 실제 코드·로그·실측으로 확인한다. 사실마다 근거(파일:줄, 실행한 명령과 결과)를 남긴다.
   추측으로 현재 흐름을 쓰지 않는다.
2. **틀 고르기.** 파일마다 틀 하나를 고른다 (아래 결정 규칙 "틀").
   - **변경형** `files/spec-template-change.md` — 이미 있는 동작을 고친다. 뼈대 **현재 흐름 → 고칠 곳 → 바뀐 흐름**.
   - **신규형** `files/spec-template-new.md` — 고칠 현재가 없다. 뼈대 **목적과 쓰는 사람 → 만들 것 → 기존과 붙는 곳**.
3. **크기 판단.** 다 쓰면 4,000자(5분)를 넘을 것 같으면 `00-개요` 에는 큰 그림만 두고 단위별로 `01-`, `02-` 로 쪼갠다.
   각 파일이 각각 5분 안에 읽혀야 한다.
4. **작성.** 고른 틀의 템플릿을 따른다.
   - 맨 앞에 **용어표**. 본문에 나오는 약어·영문 용어·앱 이름 중 사용자가 모를 수 있는 것은 전부 여기서 한 줄로 푼다.
   - 내부 코드명(P1, D4, Q3, AC-10 같은 것)을 만들지 않는다. **우리말 이름**으로 부른다
     (`D4` → "결정 기록 먼저 쓰기").
   - 실측표·대안 비교 같은 상세는 핵심 결론 한 줄만 본문에 두고, 꼭 필요하면 쪼갠 명세로 보낸다.
   - **테스트 목록**: 바뀐 흐름(신규형은 만들 것) 항목마다 `조건 → 기대 결과` 한 줄 이상(종류: 로직·화면·설정). 명세를 확정할 때
     무엇을 증명할지도 함께 확정된다. 쪼갠 경우 `00-개요` 에는 단위를 잇는 확인을 둔다.
5. **html.** `python3 ~/.claude/skills/spec-write/files/to_html.py <폴더>` 로 md 마다 같은 이름의 읽기 전용 html 을
   만든다(한 파일 완결, 라이트·다크). md 를 고칠 때마다 다시 돌린다.
6. **검사.** `python3 ~/.claude/skills/spec-write/files/check.py <폴더>` 를 돌려 전부 통과할 때까지 고친다 (아래 "완료 기준").
7. **보고.** md·html 경로를 알려 준다. 정할 것이 남았으면 명세서에 질문 목록으로 쌓지 말고,
   **대화로 하나씩 차례대로** 설명하고 묻는다. 정해지면 본문을 그 결론으로 고친다.
8. **개정.** 사용자가 이해 안 되는 곳을 짚으면 그 곳은 명세서의 결함이다 — 설명을 채팅으로 끝내지 말고 본문을 고친다.
   개정 이력("N차 반영", 변경 내역)은 남기지 않는다. **최종본만** 둔다. 폐기한 안은 본문에서 지운다.
9. **확정.** 사용자가 더 보완할 것이 없다고 하면 확정이다. 그러면 `files/plan-template.md` 로 `구현계획.md`(+html)을 만든다:
   구현 단위(PR) 목록, PR 마다 맡을 테스트 목록 줄과 커밋 마일스톤. 테스트 목록의 모든 줄이 어느 PR 엔가 들어간다.
10. **멈춘다.** 구현은 사용자가 지시할 때 `spec-build` 매뉴얼로 PR 하나씩 시작한다.

## 결정 규칙

- docs 만 바꾸나? → 이 매뉴얼 불필요. `.claude/`·`AGENTS.md`·`CLAUDE.md` 가 걸리면 docs 아님.
- 리뷰 지적 수정이고 그 PR 에 명세서가 있나? → 불필요. 명세 범위를 벗어나면 필요.
- 이미 있는 동작이 기록된 의도와 다른 버그인가? → 불필요, `bug-fix`. 새 동작이 생기면 필요.
- 4,000자 넘나? → 쪼갠다. 줄이기 어렵다고 5분 기준을 늘리지 않는다.
- 용어를 풀어 쓰기 어렵다? → 그 용어를 쓰지 않는 문장으로 바꾼다.
- 틀: 사용자가 지금 보는 동작이나 지금 저장되는 데이터가 바뀌나? → 변경형. 기존은 그대로 두고 새것만 더하나? → 신규형.
- 틀이 섞인다(예: 기존 앱에 새 화면 추가)? → 새 화면 자체는 신규형, 기존 메뉴·권한·테이블에 붙이는 연결은 `기존과 붙는 곳` 에 근거와 함께.
  붙이려고 기존 동작을 바꿔야 하고 그 변경이 한 줄 설명을 넘으면 그 부분만 변경형 파일로 쪼갠다. 한 파일에 두 틀의 절을 섞지 않는다.
- 쪼갠 폴더 안 파일마다 틀이 달라도 된다. `00-개요` 는 폴더 전체의 중심이 고치기면 변경형, 만들기면 신규형.
- 현재 흐름·기존과 붙는 곳을 확인 못 했다? → 확인 못 했다고 명세서에 적고 사용자에게 묻는다. 추측으로 채우지 않는다.
- 구현 중 명세와 다르게 가야 한다? → 명세서를 먼저 고치고 사용자 확인 뒤 구현한다.
- 비용을 줄이려고 품질(검토 횟수·범위·모델)을 깎는 안인가? → 추천하기 전에 품질 영향을 실측한다
  (빠지는 결과가 실제로 쓸모 있었는지, 대안이 정말 싼지). 실측 없이 "절감"만으로 추천하지 않는다.

## 완료 기준 (check.py 가 1~8 을 검사)

1. 폴더 안 모든 md 가 본문 4,000자 이하 (코드 블록 제외)
2. 모든 md 에 `용어` 절이 첫 절로 있다
3. 모든 명세 md 가 두 틀 중 하나의 절을 다 갖는다 (`구현계획.md` 제외) — 변경형 `현재 흐름`·`고칠 곳`·`바뀐 흐름`,
   신규형 `목적`·`만들 것`·`기존과 붙는 곳`. 두 틀의 절을 섞으면 실패
4. 내부 코드명 패턴(`P1`, `D4`, `Q3`, `AC-10` 등) 0건
5. 개정 이력·미결 표시(`N차`, `반영 이력`, `TBD`, `미정`) 0건
6. md 마다 같은 이름의 html 이 있다
7. 모든 명세 md 에 `테스트 목록` 표가 있고 줄마다 `조건 → 기대 결과` 다 (빈칸·자리표시 없음)
8. (확정 뒤) `구현계획.md` 의 PR 마다 `테스트:` 줄이 1개 이상 있다
9. (사람이 확인) 현재 흐름·기존과 붙는 곳의 사실마다 근거가 있다, 테스트 목록의 모든 줄이 어느 PR 엔가 들어갔다

## 하지 않는 것

- 명세서 없이 구현 시작, "간단하니까" 예외 두기
- 워크트리 안 `.requirements/` 에 쓰기
- 질문 목록을 명세서에 쌓아 두고 사용자가 읽게 하기
- 기존 `.requirements/` 설계서 소급 정리 (새 설계부터 적용)
